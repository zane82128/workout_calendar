# PWA 更新與發版規格

狀態：驗收中（本地實作已建立，手機安裝模式與正式部署待驗收）。建立日期：2026-10-19。

本文件定義更新機制、發版步驟與驗收條件。npm 指令、CI 工作流程及更新介面已加入 repo；尚未啟用線上部署，也尚未完成 Android／iOS 實機驗收，因此不標記為完整驗收通過。

## 1. 目標與邊界

- 在原本的正式網址持續提供更新，不要求用戶重新安裝 PWA 或清除網站資料。
- 連線使用時能檢查、下載並提示更新，避免長期無提示地停留在舊版。
- 更新前後保留訓練動作、紀錄、備忘錄及計時器狀態。
- 正在輸入或訓練時不自動重新整理，由用戶選擇套用時機。
- 離線、App 未開啟、下載失敗或用戶選擇稍後時，允許繼續使用目前版本；不承諾所有用戶同時更新。
- 本階段不包含強制更新、遠端推播、帳號同步或訓練資料雲端備份。

### 首次 GitHub Pages 設定與手機安裝

以下由原 `github_pages_pwa_steps.md` 整合，部署說明只維護本文件。

1. 安裝 Node.js 24，於 repo 根目錄執行 `npm ci` 及 `npx playwright install chromium`。
2. 核對 `release.config.json`、正式入口及 worker scope。
3. 首次切換時，在 GitHub Settings → Pages → Build and deployment 將 Source 設為 GitHub Actions；這項帳號設定尚未由本地程式自動修改。先確認切換，再 push 到既有發布分支，避免舊的分支式部署直接發布來源檔案。
4. 確認 Actions 可執行、`github-pages` environment 允許 main 部署，依實際保護規則完成審核。只有確認 Pages 已切換後，才能將一般 push 視為僅檢查、不部署。
5. 手機候選版本驗證完成後，依第 7 節手動執行 `Release PWA`；確認 build、deploy、record 三項工作成功。

手機安裝：Android Chrome 開啟正式 App 網址，選擇安裝或加到主畫面；iPhone Safari 開啟同一網址，選擇分享 → 加入主畫面。安裝不等於資料已有外部備份。

實作前須核對並記錄以下部署設定，不從說明文件推測線上設定：

| --- | --- |

| 發版分支 | 本地為 `main`，新工作流程限制此分支；既有 Pages 後台設定仍須核對 |

維持相同 origin，並保持既有入口及資源路徑可用。不得為導入自動化而直接搬動正式入口。

## 3. 版本與部署產物

- 版本採 `YYYY.MM.DD.<當日序號>`，例如 `2026.10.19.1`；日期使用 Asia/Taipei。同一日每次正式發版遞增序號。
- 每份產物包含 release ID、Git commit SHA、建置時間及資料格式版本；畫面可查看「目前版本」。
- 由單一版本來源生成畫面、版本資訊檔與 Service Worker 的版本，禁止人工維護多份互相獨立的版本字串。
- JS/CSS 及其模組依賴使用內容雜湊檔名，建置工具同步重寫引用；HTML、manifest、圖示與所有離線必要依賴納入資源清單。
- `sw.js` 保持穩定 URL，不以變更註冊網址作為版本切換手段；每個 release 產生有差異的 worker 內容。
- 建置輸出至 `dist/`，不得修改開發用的 `src/`。同一次驗證及部署使用同一份產物，不在部署前重新產生另一份。
- 版本資訊檔使用網路讀取、不納入快取優先流程；網路錯誤時不得宣稱已是最新版。版本資訊僅供顯示與診斷，以已安裝完成的 worker 判斷是否可套用更新。
- 保留可回復的正式產物與對應 commit；正式部署不得包含尚未提交的來源修改。

## 4. 用戶端更新行為

### 檢查時機與狀態

1. 啟動並完成 worker 註冊後檢查更新，同時檢查是否已有 waiting worker。
2. App 回到前景或網路恢復時再次檢查；兩次自動檢查至少間隔 5 分鐘（300 秒），避免短時間重複請求。此為事件觸發的最短間隔，不是每 5 分鐘固定輪詢。
3. 提供「檢查更新」按鈕，可略過上述節流，但不得重複啟動並行檢查。
4. 註冊設定使用 `updateViaCache: 'none'`，主動透過 registration 更新檢查；這不取代應用資源本身的版本管理。
5. 狀態包含：檢查中、下載中、更新已準備完成、目前沒有可用更新、離線無法檢查、更新失敗。
6. 首次安裝不顯示「有新版本」。只有完整下載且安裝完成的新 worker 才可提示套用。

### 套用更新

- 顯示「新版本已準備完成」及「立即更新／稍後」；選擇稍後不持續彈窗，保留可再次操作的更新入口。
- 訓練計時中顯示「更新將重新載入畫面，計時會保留」；重新載入後以時間戳還原計時，已到期的休息計時最多觸發一次完成處理。
- 用戶選擇更新後，先儲存輸入內容、選定日期、所在頁面與計時狀態。儲存失敗時取消套用並提供錯誤訊息，不清除資料。
- 儲存成功後才通知 waiting worker 執行 `skipWaiting`；監聽 `controllerchange`，確認接管後重新載入一次，禁止重整迴圈。
- worker 不在一般安裝路徑中無條件呼叫 `skipWaiting`。首次啟用不觸發更新重整。
- 多分頁以 BroadcastChannel 或等效方式協調：套用前各頁儲存狀態並確認；有無法確認、未儲存內容或其他頁正在計時時，提示先關閉其他頁，暫緩啟用。不得使其他頁靜默遺失輸入或重整。
- 保留目前資料模型的相容性；還原更新狀態時，不得被「進入 Schedule 回到今天、重新啟動 Session Timer」的既有流程覆寫。

## 5. 快取與資料保護

- 新 worker 安裝時完整下載本版必要資源；任一必要資源失敗即視為安裝失敗，繼續使用舊版，不顯示更新完成。
- 每個 release 使用獨立、具有本專案前綴的快取。只清理本專案所擁有的舊快取，不刪除同 origin 的其他應用快取。
- HTML 與 JS/CSS 必須來自相容版本，避免線上新 HTML 搭配舊程式；導覽應提供目前啟用 release 的快取入口。新版本在背景安裝完成後再切換。
- 舊頁仍可能請求舊的延遲載入資源；實作須保留需要的舊資源，直到舊頁不再使用，或由部署策略提供相容資源。不得在仍有舊頁時直接清空其依賴。
- 更新不得呼叫 `localStorage.clear()`、刪除訓練資料，或以清除網站資料作為標準更新步驟。
- 應用版本與資料格式版本分開管理。資料格式有變更時，須先保留本地原始資料備份，再做可驗證的遷移；失敗不得覆寫原始資料。
- 本地備份不等同外部備份，無法防止用戶清除網站資料。資料匯出／匯入屬另案功能。
- 一般發版優先採向後相容的資料變更；破壞性資料變更須另寫遷移及回復計畫，不能直接沿用一般回復流程。

## 6. 自動化介面

指令已實作，使用 Node.js 24。PowerShell 若阻擋 `npm.ps1`，可使用 `npm.cmd` 執行相同指令，不必放寬系統執行原則。

```powershell
npm ci
npx playwright install chromium
npm run release -- --release 2026.10.19.1
npm run preview
```

預覽網址為 `http://127.0.0.1:5173/workout_calendar/src/`。第一次安裝工具後不必每次重裝瀏覽器。`release` 會驗證明確指定的 ID，實際正式發版請使用未用過的日期與序號。`dist/` 是部署根目錄，包含 `src/`，不可只上傳 `dist/src/` 而改變入口。

單獨使用時：`npm run build -- --release <ID>`、`npm run check:release`、`npm run test:update`。後兩者檢查現有 `dist/`，不重建候選產物。升級測試會另外建立隔離的 A 版與回復版，結果在 `.release-tests/results.json`。

本地未提交修改可以建立測試候選版本，產物會標記 `sourceDirty`；正式工作流程設置 `FORMAL_RELEASE=1`，拒絕未提交修改、不同 commit 的產物或重複版本。正式部署成功後建立 `pwa-<ID>` tag；也會核對線上版本避免重用目前已部署 ID。日期由發版者按 Asia/Taipei 指定，工具驗證日期與序號格式。

| 指令／流程 | 責任 |
| --- | --- |
| `npm run build` | 依指定 release ID 與 commit 產生完整 `dist/`，生成資源清單與版本資訊 |
| `npm run check:release` | 檢查引用、base path、快取清單、版本一致性及產物完整性 |
| `npm run test:update` | 使用持續保留資料的瀏覽器環境驗證 A 版升級 B 版及失敗情境 |
| `npm run release` | 本地依序執行建置、產物檢查及升級測試；不自動 commit、push 或部署 |
| GitHub Actions | 對目標 commit 執行相同檢查；僅成功後部署已驗證產物，序列化正式部署，避免舊工作覆蓋新版 |

release ID 由發版時明確指定，工具檢查格式與重複；CI 使用相同 ID。依賴以 lockfile 和 `npm ci` 安裝。PR 只檢查不部署；正式發版由目標分支上的手動工作流程指定 release ID 觸發，避免每個一般 push 都成為正式發版。

## 7. 每次正式發版 SOP

### 發版前

- [ ] 工作目錄乾淨，確認目標 commit、正式網址、base path 與 release ID。
- [ ] 完成功能驗證；若改變資料格式，附上遷移、備份與回復驗證。
- [ ] 指定 release ID 執行 `npm run release`，所有檢查通過。
- [ ] 驗證現有公開版本升級至候選版本，保留舊快取與原本資料，不以全新瀏覽器測試替代。
- [ ] 檢查 Android Chrome 與 iOS Safari 的已安裝 PWA：更新提示、套用、重新開啟、離線使用與資料保留。
- [ ] 保留上一個穩定版本的產物與 commit，記錄本次變更。

### 部署

- [ ] 將已驗證 commit push 至 `main`，等候一般 CI 通過；push 本身不部署。
- [ ] 在 GitHub Actions 手動執行 `Release PWA`，選擇 `main`、指定同一 release ID，並確認已完成手機驗證。
- [ ] 確認 CI 檢查與 Pages 部署成功，記錄產物版本、commit、工作流程執行連結及時間。
- [ ] 若候選來源或產物有變更，重新驗證，不沿用上一份驗證結果。

### 部署後

- [ ] 正式網址的版本資訊與本次產物一致，必要資源無 404。
- [ ] 保留舊版安裝的裝置連線開啟後，可看到更新提示並切到本次版本。
- [ ] 訓練紀錄、備忘錄、日期、所在頁與計時狀態符合預期。
- [ ] 關閉再開啟仍是本次版本，離線開啟正常，無持續提示或重整迴圈。
- [ ] 於發版紀錄寫入測試平台與結果；全部完成才標記發版驗收通過。

## 8. 驗收案例

| 案例 | 必須符合的結果 |
| --- | --- |
| 全新安裝 B | 正常開啟、顯示 B 版本、無錯誤更新提示；預快取完成後可離線操作 |
| 舊版 A → B | 保留 A 的 worker、快取與資料，連線開啟後完成檢查並提示；套用後顯示 B，資料一致 |
| 目前公開舊版 → 首次新版 | 不要求清除資料或解除安裝；驗證既有 worker 能安裝新 worker。舊程式沒有提示時，可能須關閉所有舊視窗再重開；記錄實際首次升級步驟與限制 |
| 稍後更新 | 保持 A 正常使用，可從更新入口再次套用 B |
| 輸入中／計時中 | 不自動重整；選擇套用後輸入與計時正確還原，休息完成不重複觸發 |
| 多分頁 | 未儲存或計時中的其他頁阻止直接套用；符合協調條件後可完成升級，其他頁不遺失資料 |
| 離線／檢查失敗 | 保持 A 可用，明確顯示無法檢查，不誤報最新版 |
| B 缺檔／下載中斷 | 安裝失敗並繼續 A；不提示 B 已準備完成，恢復後可重試 |
| 儲存失敗 | 不啟用 B、不重整、不清資料，顯示可理解的錯誤 |
| 重複檢查／重開 | 無重複下載工作、提示堆疊或無限重整 |
| 非根目錄部署 | 正式 base path 下的 HTML、模組、manifest、圖示、worker 與離線入口皆正確 |
| 回復版本 | 以新 release ID 發布穩定程式後，B 用戶可收到提示並套用；資料保持相容 |

自動測試至少涵蓋正常 A → B、資料保留、首次安裝、離線、缺檔失敗與重整迴圈。瀏覽器測試不得開啟 DevTools 的強制更新選項來掩蓋真實行為；手機安裝模式另做人工驗證。

## 9. 更新失敗與回復

1. 先確認用戶目前版本、網路、正式部署版本，以及 worker 是否正在下載或等待啟用。
2. 優先使用 App 的「檢查更新」及更新入口；首次導入新版更新機制時，必要時請用戶關閉所有同站視窗再重新開啟。
3. 不把清除網站資料、解除安裝或直接修改用戶紀錄當作一般排障方式。
4. 正式版有問題時，將已知穩定程式建置成「新的 release ID」重新部署，使有問題版本的用戶也能偵測到修復更新。
5. 回復前確認穩定程式能讀取目前資料格式；不相容時先提供相容修復版，不直接回退。
6. 回復也須通過產物及升級檢查，記錄影響版本、處理方式與驗收結果。

## 10. 實作順序與完成條件

1. 核對現有部署網址、scope 與分支，建立可重現的建置產物及版本資訊。
2. 實作快取清單、完整安裝與版本一致性。
3. 實作更新提示、狀態儲存還原、多分頁協調與手動檢查。
4. 建立舊版升級測試及 GitHub Actions，完成手機驗收。
5. 更新 README 與部署文件，移除已失效的手動版本及清除資料建議；首次正式發版保留實際驗證紀錄。
